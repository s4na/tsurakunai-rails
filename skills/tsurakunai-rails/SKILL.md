# つらくないRails

日常の変更で責務、依存、副作用を増やしすぎないための設計方針を標準で適用する。動作するコードでも方針から外れれば設計上の指摘を行う。不具合とは区別し、具体的な処理と最小の改善案を示す。導入先の明示的な規約・個別OFF・今回の依頼範囲を優先する。

## 実行とレビュー

1. 依頼と差分、導入先のAGENTS.md・CLAUDE.mdなどの規約、lint設定、テスト入口を確認する。未コミット変更を保護する。
2. [日常の設計方針](references/daily-design.md)を読み、変更に関係する標準方針と個別OFFを確認する。コントローラーの業務処理、モデルからのPORO分離、純粋な計算、ViewComponent、クエリ、外部・重い処理、命名を確認する。変更していないコードを全件改修しない。
3. 導入済みのlintと変更に適したテストを実行する。このGemが導入済みなら`bundle exec tsurakunai-rails check -- <テストコマンドと引数>`を使う。ERB設定と依存も導入済みなら`check --views -- <テストコマンドと引数>`を使う。未導入・未実行を成功と扱わない。
4. 必要なガイドを下から選び、呼び出し元、schema、描画結果、保存結果を追う。設計推奨を満たすために認可・不変条件・失敗時の挙動を壊さない。依存追加や新しい基盤の導入は依頼範囲と権限を確認する。
5. 修正依頼では最小の変更と必要な検証を行う。レビュー依頼では編集しない。既存テストが動作を保証するなら、網羅性だけを理由にテストやクラスを増やさない。
6. 不具合、設計方針からの逸脱、実行結果、未確認事項を分けて簡潔に報告する。lint成功は設計レビューの完了を意味しない。CIはAIの判断を実行しない。

## 指摘する条件

設計上の指摘には、方針名、対象のファイルと行、処理内容、なぜ対象になるか、例外・OFFの有無、最小の改善を示す。方針で認める例外を欠陥扱いしない。クラス数や行数を閾値に全メソッドの移動を要求しない。

不具合には、発生する入力・状況、期待と実際の差、利用者やデータへの影響、最小の修正と検証を示す。性能や脆弱性は証拠なしに断定しない。不明な仕様は具体的な質問にする。

RuboCopは設計方針8ルールと事故防止8ルールが標準で有効。RSpec7ルールも標準ON。ERB利用アプリでは設定と依存を導入し`--views`を使う。未導入の場合は必要な設定を説明し、依頼範囲・権限を確認する。構文の違反は不具合の証明ではなく、正当なcallback、業務属性、bulk更新などはAllowedMethods・対象範囲・個別OFFで調整できる。OFFにするためだけに大規模改修や例外の報告書を要求しない。

日常の設計方針をOFFにしても、認可漏れやデータ破損の具体的な問題は確認する。Gem設定やスキルは外部操作・push・デプロイの権限を増やさない。
