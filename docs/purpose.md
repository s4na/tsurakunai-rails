# なぜ「つらくないRails」を作るか

## 対象と価値

Railsに強い人の設計判断を毎回要求しない。中規模・大規模になり、経験・好み・参加時期が異なる人が加わっても、同じ仕事を似た形で書き、初めて触る機能を入口から追えるチームを対象にする。

2026-10-06の依頼で明確になった趣旨は、便利な機能を何でも許したうえで熟練者に適切な使い分けを求めることではない。入力・実行順序・責務を隠すRailsの使い方を規約で制限し、その範囲で業務の表現と変更をのびのび行えるようにすること。「つらさ」を、同じ変更に流儀が混在すること、暗黙の前提を探すこと、レビュー担当者ごとに判断が変わることとして扱う。

Goのように書き方が揃う方向を参考にするが、RailsへGoの階層を輸入したり、全CRUDをServiceへ包んだりしない。開発者が日常の変更で選ぶべき道を減らし、例外をチーム全体の決定として見えるようにする。

「どうあるべきか」と「どうでないべきか」の両方で書き方を揃える。ルールに必須の形・契約と禁止形を定め、実装スキルとレビュースキルにも両方を適用する。禁止構文がないコードでも、同じ責務・入力・失敗契約に揃っていなければ合格にしない。検査できない意味上の規約を、任意の助言へ戻さない。

## 37signals・DHHとの関係

37signalsの記事はcallback、Current、Concernの有用な使い方を説明している（[一次資料](https://dev.37signals.com/globals-callbacks-and-other-sacrileges/)）。その会社やDHHの技量を客観評価したものではなく、「異なるチームに同じ使い分けを要求してよいか」は別の判断である。本パッケージは、特定企業の実装で使われていることを標準許可の理由にしない。

過去の調査は[調査記録](../skills/tsurakunai-rails/references/daily-design.md#調査から採用したこと)に残す。そこで観測したコードと、本パッケージで採る[チーム規約](../skills/tsurakunai-rails/references/team-policy.md)を区別する。

## 支払う価値を問う基準

価値はルール数、文章量、lint指摘数、特定企業への近さでは測らない。次を実際の変更で確かめる。

- 初めての担当者が、CRUD・状態遷移・複数集約のどれを選ぶか、置き場所と失敗契約を決められる。
- 実装とレビューが同じ規約IDを使い、担当者の好みでcallback・Concern・partialの許可が変わらない。
- lintが「避ける構文」を実際に拒否し、必要な認証hook等を残せる。直し方と検査の限界も分かる。
- 新しい層・依存・手作業の報告が、減らした探索・議論の負担を上回らない。
- 配布Gemと配置されたスキルで同じ規約・検査が使え、既存アプリへ動作を保って段階導入できる。

本番チームでの時間削減・支払意思はまだ観測していない。技術的な受け入れ条件を満たすことと市場価値が実証されたことを混同しない。未検証の効果を広告文句にせず、[改善フロー](improvement.md)で実例と残件を追う。
